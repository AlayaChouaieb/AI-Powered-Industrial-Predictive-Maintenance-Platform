## 2. Preprocessing and split (Day 3)

- **Inputs (API contract order):** `product_type` + air_temperature_k, process_temperature_k, rotational_speed_rpm, torque_nm, tool_wear_min.
- **Derived features** (functions of the inputs only): `temp_diff_k`, `power_w`, `strain_minnm`. Compared against raw-only in section 3.
- **Everything is inside an sklearn `Pipeline`**, so scaling/encoding is fit on training rows only (also inside each CV fold). `tests/test_pipeline.py` checks that the scaler mean equals the training mean and not the full-data mean.
- **Imbalance:** `class_weight` (`balanced` for Logistic Regression, `balanced_subsample` for Random Forest); no resampling, so no synthetic rows can leak into evaluation.
- **Split:** stratified on `fault_class`, 60/20/20, seed 42, stored as UDI lists in `data/processed/split.json` together with a content hash of the dataset. The **test split is not loaded by any Week 1 computation**; it is reserved for Day 15.

## 4. Anomaly detector (Day 5)

- **Model:** Isolation Forest, 300 trees, trained **only on normal training rows** (`fault_class == none`, 5797 rows). Failure rows never enter training.
- **Score:** `-score_samples` (higher = more unusual).
- **Threshold rule:** the 95th percentile of the scores of validation normal rows, i.e. a 5% false-alarm budget. Chosen on validation data as the roadmap requires; the budget itself is a judgement call, so the full trade-off is shown below.
- **Evaluation:** failure labels are an **imperfect proxy**: "unusual" is not the same as "about to fail".

The classifier answers "which known failure mode is likely?"; the anomaly detector answers "is this operating point unusual?". They are complementary, but the anomaly signal is far noisier.

## 6. Feasibility gate decision

**Pass, with a narrowed promise.**

1. **Promise:** a failure-risk score and a likely failure mode for **HDF, PWF and OSF**. Stored as `supported_fault_classes` in `models/model_card.json`.
2. **Not promised:** TWF prediction and the `other` class. Show tool wear as a rule-based advisory instead; list both as future work.
3. **Anomaly detector:** keep as a secondary signal, labelled low-confidence (22% precision at the chosen threshold). If time is tight in Week 3, it is a safe cut after SHAP.
4. **Wording for the UI/README:** "decision-support score trained on synthetic data", never "probability of failure".

## 7. Week 1 demo

`python scripts/week1_demo.py` scores five hand-built scenarios and replays validation rows with simulated machine IDs. Captured output: `reports/week1_demo_console.txt`. Observations:

- Normal operation -> healthy; high-power and high strain x torque scenarios -> critical with the right mode (PWF, OSF).
- The HDF-rule scenario is critical (risk 0.34) but the arg-max class is `none`: the forest only approximates the exact rule near its boundary. A rule engine would be exact on this synthetic data; the model's value is the pipeline and the interface, not new physics.
- A tool-wear-only scenario (235 min) is healthy: consistent with TWF being unpredictable here, and the reason for the advisory rule.

## 8. Limitations and honesty notes

- **Synthetic data.** Results do not show performance on real equipment.
- **Rule-derived labels.** HDF/PWF/OSF are exact functions of the inputs, so metrics are an upper bound on real difficulty.
- **Small classes.** TWF (26 train rows) and `other` (19) are too small for reliable per-class estimates; no confidence intervals were computed in Week 1.
- **No temporal structure.** AI4I has no timestamps or machine IDs; the split is random, not chronological.
- **Single seed**, no hyper-parameter search beyond three RF leaf sizes.
- **Test split untouched.** All numbers are cross-validation or validation; final test metrics come on Day 15.
- **Data source.** The CSV used here was downloaded from a GitHub mirror (UCI was not reachable from my environment). It matches the UCI documentation on row count (10,000), column set and the HDF/PWF/OSF counts, and has 339 failures; file SHA-256 `59db4f1d9c34c58136d89e5a006ec190dcea19e9dbea74f6b3b0c6f22a44d183`. Please run `python -m pm_ml.download_data` on your machine and confirm the content hash `6b951bfedd1c42a767117b2bc326e4e3fceac080c7c8a9d87655a46d3dc45a63` matches (`tests/test_pipeline.py` checks this against the stored split).
